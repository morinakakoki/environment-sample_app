# インフラ判断ドリル 共通仕様（全ケース共通・厳守）

## 0. これは何か
AWS基盤の設計〜運用を担当するインフラエンジニアの「判断力」を鍛える4択ドリル。
形式の下敷きはIPA高度試験 午後Ⅰ（ITサービスマネージャ／システムアーキテクト）の事例問題。
知識クイズではなく、**同じ知識量の人間の間で差がつく「優先順位・前提の置き方・手続きの踏み方」**を問う。

## 1. 受験者の背景（出題範囲の制約・厳守）
- 経験工程は**基本設計以降**：AWS基盤の基本設計／詳細設計（パラメータ設計含む）／導入設計・移行／テスト（SIT・性能試験）／運用・障害対応
- **要件定義・顧客折衝・アプリ開発は未経験**。これらを主題にした問いを作ってはならない。
  - ただし「基本設計の中で顧客に選択肢と数字を提示して決めてもらう」「未定義のRTO/RPOを定義させるための材料を作る」は範囲内（ケース5・6で明示的に指定されている）。
  - 禁止：要件のヒアリング手法そのもの、契約・見積・受注の話、アプリのコード実装・フレームワーク・SQLチューニングの実装詳細。
- 題材：EC2／RDS／ALB／VPC／IAM／CloudWatch／CloudFormation の標準的な構成。オンプレ→AWSの導入・移行も可。
- 登場人物・組織はすべて仮名（A社、B部、運用チーム、業務部門、上司、PM、顧客 等）。**実在企業名・製品の固有ブランド名（AWSサービス名を除く）は使用禁止**。

## 2. 1ケースの構造
1ケース＝**連問3問**。同一シナリオが続き物で進む。
- **問1**：初動または方針の判断（「最初に何をどの順でやるか」「どう設計判断を進めるか」）
- **問2**：**前提を1つだけ**変えた再判断。問1の正解がそのままでは通らなくなる／優先順位が入れ替わるように前提を変える。
- **問3**：その判断で**捨てたもの・残るリスク**を問う。正解は「捨てたものを正しく認識し、それに対する手続き（記録・合意・期限・監視）を取る」もの。

## 3. 選択肢の作り方（最重要・厳守）
- **4つとも、実務で誰かが実際に言いそう・やりそうな案**にする。明らかなハズレ（法令違反、荒唐無稽、無関係、あからさまな怠慢）を**1つも入れない**。
- 4択の差は次の**いずれか1つ**に宿らせる：
  - **優先順位**（やること自体は正しいが順番が違う／後回しでよいものを先にやっている）
  - **前提**（確認していない事実を確定として扱っている／前提が変わったのに前の判断を引きずっている）
  - **手続き**（合意・記録・報告・期限の設定を飛ばしている／権限のない者が単独で決めている）
- **不正解3つは、それぞれ別の失点理由**を持たせる（例：1つは順序、1つは未確認の前提、1つは手続き飛ばし）。3つが同じ理由で落ちるのは失敗。
- 不正解の中に**1つは「一見いちばん誠実・勤勉に見えるが、優先順位を外している」案**を必ず入れる（例：初動で原因究明に全力を注ぐ、その場で完璧な恒久対策を設計する）。
- **正解にも痛みを持たせる**（何かを捨てている、コストや手間がかかる、誰かに嫌がられる）。「全部いいとこ取り」の選択肢を正解にしない。
- 文体・長さを4つで揃える：**各60〜110字程度**、末尾は「〜する。」で統一。体言止め・箇条書き禁止。
- 「すべて」「必ず」「絶対に」「一切」等の強い断定語で不正解が見破れるようにしない。使うなら正解側にも使う。
- 選択肢の順序は指定された正解位置に従う（別途プロンプトで指定）。正解が長い／短いといった長さの偏りを作らない。

## 4. 問題文の作り方
- ケース冒頭の**状況文（scenario）は250〜400字**。IPA午後Ⅰ風の事例文体（常体「〜である」「〜した」）。
  - 構成：システムの構成と役割 → 直前の出来事・制約（時刻、期限、体制、変更管理、連絡可否）→ あなたの立場。
  - **判断に必要な事実だけを書く**が、**あえて確定していない事実**（未確認、記録なし、連絡つかず）を1つ以上残す。ここが問1の勘所になる。
  - 技術的に嘘を書かない。AWSの挙動（Multi-AZ RDSの自動フェイルオーバー、EBSのオンライン拡張、ALBのヘルスチェック、CloudWatchメトリクスの粒度など）は実際の仕様に忠実に。
- 各問の `lead`：問2・問3で追加される前提・状況の変化を60〜160字で書く（問1は空文字でよい）。
- 各問の `prompt`：問い文。40〜90字。「あなたはまず何をするか」「どう判断すべきか」等、単一の判断を問う。

## 5. 講評（解説）の作り方
- `explain`（正解の根拠）：**200〜320字**。なぜこれが最善か、どの原則・順序に基づくかを説明する。「正解にも痛みがある」ことに触れる。
- `others`（不正解3つ）：各**90〜160字**。**なぜ劣るか**を、それぞれ**異なる失点理由**（順序／前提／手続き）で明示する。「間違い」ではなく「実務では通るが、この場面では順位が下がる理由」を書く。人を責める書き方をしない。
- `frame.howto`：指定された判断フレーム名の**適用手順を2〜4文**、120〜220字。フレーム名は**指定された文言を一字も変えずに使う**。
- `interview`：面接でそのまま口に出せる**ちょうど3行**。各行**45〜75字**。
  - 1行目＝状況（何が起きていたか／何を任されていたか）
  - 2行目＝自分の判断と根拠（「私は〜と判断しました。理由は〜」）
  - 3行目＝結果と学び（「結果〜。以後は〜するようにしています」）
  - 一人称は「私」。読み上げて自然な話し言葉。専門用語は使ってよいが、面接官に通じる範囲に留める。
- `principle`（今日の判断原則）：**指定文言をそのまま使う。一字も変更禁止。**

## 6. 出力フォーマット（JSONファイル1本）
指定パスに **UTF-8のJSONのみ**（マークダウンのコードフェンス無し、コメント無し）を書き出す。

```json
{
  "id": 1,
  "field": "障害対応",
  "title": "月曜9時の応答遅延",
  "scenario": "…（250〜400字）",
  "frame": { "name": "…（指定文言そのまま）", "howto": "…（120〜220字）" },
  "principle": "…（指定文言そのまま）",
  "interview": ["…", "…", "…"],
  "questions": [
    {
      "no": 1,
      "lead": "",
      "prompt": "…",
      "choices": ["…", "…", "…", "…"],
      "answer": 0,
      "explain": "…",
      "others": [
        { "i": 1, "text": "…" },
        { "i": 2, "text": "…" },
        { "i": 3, "text": "…" }
      ]
    }
  ]
}
```
- `answer` は 0=A / 1=B / 2=C / 3=D。**プロンプトで指定された位置に必ず置く**（正解記号の分布を全体で均すため）。
- `others` は `answer` 以外の3つのindexを**昇順で全て**含める。
- プレースホルダ（「TODO」「…」「（ここに書く）」等）禁止。全項目を完成させる。

**自分の担当ケース以外の題材に踏み込まない。**他ケースと選択肢の文言・言い回しが被らないよう、担当ケース固有の技術要素・登場人物・時間軸で書き分ける。
特に「関係者に第一報を入れる」「記録に残す」といった共通動作は、**ケースごとに具体の宛先・媒体・粒度を変えて**書く（例：ケース1は業務部門への影響連絡、ケース4は上長への自己申告、ケース8は設計レビュー記録、ケース11はテスト計画の合意記録）。
