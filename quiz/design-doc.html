3処理方式

項目方式備考
実行形態バッチ。Cloud Scheduler → Cloud Run Jobs（起動→処理→終了）。常駐プロセス無しAirflow／Composer は不採用（コスト）
スケジュール日足・マクロ：火〜土 07:00 JST（米国市場の翌朝）／ファンダ：週1／staging・mart：raw の 30 分後に順次順序制御は時刻ずらし。S-5-1 で mart 実行方式を選ぶ
取得Python（yfinance / requests）→ pandas DataFrame → BigQuery Load JobSEC は User-Agent 必須・10 req/s、FRED は API キー
ロード（日足）WRITE_TRUNCATE：直近1年を毎回全量取り直す冪等。全量取り直せる設計だから成立（条件付き判断）
ロード（分足）日付パーティション単位の置換（table$YYYYMMDD）60日しか遡れないため全量 TRUNCATE 不可 S-3-2
変換素の SQL（staging／mart）。W8 で mart のみ dbt に置換調整後終値の再計算＝ウィンドウ関数（LAG／累積）
スキーマ正は Terraform。ロードジョブは LoadJobConfig(schema=…) で明示し autodetect を使わない8/25 スキーマドリフト事故の恒久対策
再実行手動 gcloud run jobs execute。冪等なので何度でも可再実行判断の根拠を W7 で記録

6運用・監視方式（W7）

監視項目検知方法通知対処

7コスト方式（3層）

  1. 予算アラート 月 3,000円：通知のみ。課金は止まらない 構築済
  2. 1クエリあたり maximum_bytes_billed：実行前の見積もりで止まる唯一の確実な層。mart の SQL ジョブと dbt profile に設定 S-5-8 / S-8-1
  3. カスタム割り当て（プロジェクト／ユーザー 1日）：無料トライアル中は変更不可。11/1 有料化後に設定 S-10-10

前提：BigQuery 無料枠 10 GiB ストレージ／1 TiB クエリ・月。無料トライアルは 2026-11-16 終了（$300 使い切りでもリソース停止＝課金されない）。

#論点採用採用しなかった案トレードオフ（採用案の弱点も）状態
1クラウド／DWHGCP BigQueryAWS Redshift ServerlessBigQuery は月 1 TiB／10 GiB が恒久無料、求人票でも BigQuery 必須が多い。Redshift は $300・90 日のみ。弱点：AWS 実務との接続が薄く見える → 経歴書側で CloudFormation を語る確定
2データ実データ（yfinance / EDGAR / FRED）合成データ（コールセンター KPI）合成だと品質テストが自作自演。実データは本物の欠損がある。弱点：yfinance は非公式・personal use → 実務では公式有料 API に置換すると明言確定
3実行基盤Cloud Scheduler → Cloud Run JobsCloud Composer（Airflow）／Workflows／Cloud FunctionsComposer は常駐課金で無料枠外。Jobs は起動→終了で課金最小。弱点：依存関係を時刻ずらしで持つので、ジョブが増えると破綻 → その時は Workflows確定
4日足のロードWRITE_TRUNCATE（全量置換）WRITE_APPEND／MERGE1年分を毎回取り直す設計なので TRUNCATE が最も単純で冪等。APPEND は再実行で重複。弱点：データ量が増えると全量が無駄 → 増分設計なら MERGE確定
5分足のロードパーティション単位の置換全量 TRUNCATE／APPEND60 日しか遡れず全量不可。パーティション置換なら日単位で冪等。弱点：`$YYYYMMDD` と行の日付の不一致でエラーS-3-2
6スキーマの所有者Terraform が正、Python は明示指定Python の autodetect に任せる／Terraform でテーブルを管理しないautodetect は毎回定義を上書きしドリフト → replace 事故（8/25）。弱点：列を足す時に .tf と Python の両方を直す確定
7SAワークロードごとに専用 SA、キー無しdefault compute SA（公式例）／SA キー JSON専用 SA で最小権限（起動役は invoker だけ）。弱点：SA と binding が増えて Terraform が長くなる確定
8Terraform stateローカルGCS リモートバックエンド＋ロック個人・単一端末なのでローカルで足りる。弱点：端末紛失で state 消失、複数人不可 → 本番は GCS確定
9コスト上限3層（予算アラート／bytes_billed／割り当て）予算アラートのみ予算は通知のみで止まらない。弱点：割り当ては「おおよそ」、bytes_billed はクエリ単位で設定漏れが起きる確定
10layerraw / staging / mart（素の SQL）、mart のみ dbt全層 dbt／dbt 無しdbt の価値は ref とテスト。価値が出る mart に絞る。弱点：staging のテストが手書き ASSERT になる確定
11Snowflake縮小版（1テーブル＋スクショ）全再現トライアル 30 日で面接時にライブで見せられない。差分を語れれば足りる。弱点：Snowflake 実務相当とは言えない確定
12CI/CDやらないGitHub Actions で terraform plan6社中、要件は電通総研（歓迎）・APC のみ。3h を実装バッファへ。弱点：「PR で plan を見る運用」を語れない確定
13EDGAR の粒度—A：5項目固定 ／ B：JSON 丸ごと rawA は軽いが外国籍で欠損。B は raw 原則に忠実だが staging の SQL が重いS-2-6
14staging の実体—A：VIEW ／ B：TABLEVIEW は保存 0 だが毎回 raw を読む。TABLE は冪等・mart が軽いが二重保存S-4-2
15mart の実行—A：Cloud Run Job で SQL ／ B：スケジュールクエリ ／ C：最初から dbtA は bytes_billed を持てる。B は最短だが順序・上限が弱い。C は学習前倒しS-5-1
16失敗検知—A：ログベース ／ B：メトリクス ／ C：両方A は最短だが起動失敗を拾えない。B は拾えるがメトリクス名の確認要。C は2重S-7-1
17dim_securities の履歴Type1（上書き）SCD Type2（履歴保持）銘柄マスタの変更履歴は本ポートフォリオの分析に不要。弱点：カテゴリ変更の追跡ができない → 面接で「Type2 にするなら有効期間列を持つ」と言えるS-5-2

11Well-Architected 観点での自己評価

本書の §1〜§10 は SIer の方式設計書の型（何をどう作るか）。これを AWS Well-Architected の6本柱（GCP では Google Cloud Architecture Framework が同等）で**評価**し直した表。実務では「方式設計で書き、フレームワークでレビューする」の関係。面接で「W-A で言うと…」と接続するための対応表。

柱（AWS W-A）本書の該当この設計での実装やっていないこと（聞かれたら言う）
運用上の優秀性
Operational Excellence		§3 処理方式・§6 運用・§8 IaCIaC（Terraform）・冪等な再実行・失敗→検知→再実行判断の記録・実行履歴とログの証跡CI/CD（plan の自動化）・Runbook の整備。個人運用のため手動再実行

信頼性
Reliability		§3 冪等性・§6 監視（鮮度・品質）冪等ロード（全量置換／パーティション置換）・鮮度 ASSERT・7日連続運転の実測マルチリージョン・リトライの自動化・DR。日次バッチ1本で RPO=1日が許容のため

持続可能性
Sustainability		—該当薄。強いて言えば「読むバイトを減らす」設計はエネルギー効率と同方向本ポートフォリオの評価対象外とする
