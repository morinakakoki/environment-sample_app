1. GCP の骨格：プロジェクト・請求・API・IAM

プロジェクトは GCP の基本単位で、AWS アカウントに近い。ただし1人がいくつでも作れて、削除しても ID は再利用できない。API の有効化、課金、IAM、リソースの置き場、この4つがプロジェクト単位で決まる。本ポートフォリオは market-data-platform-4821 の1つだけ。実務では dev / prod を別プロジェクトにするのが定石で、「本番なら分ける」と言えれば足りる。

請求先アカウントはプロジェクトの親ではない。財布であって、1つの財布に何個ものプロジェクトを付けられる。IAM も継承しない。だから「プロジェクトを作る」と「請求先に紐づける」は別の操作になる。無料トライアルは請求先アカウントに付いた状態で、$300 か 90 日（今回は 11/16）で終わる。終わるとワークロードが止まる。有料化すると自動停止という安全装置が外れるので、代わりに自分で上限を置く（第2章の課金バイト、第6章のコスト3層）。

API 有効化は AWS に無い概念。GCP は各サービスを「このプロジェクトで使う」と宣言しないと呼べない。BigQuery 系は新規プロジェクトで最初から有効だが、Cloud Run / Scheduler / Artifact Registry は明示的にオンにする。Terraform では google_project_service がこれで、8/25 に apply したのはまさにこの3つ。

IAMは「誰に（プリンシパル）・どの権限の束を（ロール）・どこで（リソース）」の3つ組を並べたもの。AWS と違い、ポリシー文書を書かず、事前定義ロールをプリンシパルに直接付ける。プリンシパルには人のアカウントのほかにサービスアカウント（SA）がある。SA はメールアドレスを持つ「機械用のアカウント」で、Cloud Run Job などのリソースにアタッチして使う。AWS で EC2 に IAM ロールを付けるのと同じ絵だが、GCP では「ロール」ではなく「アカウント」なので、SA そのものにもロールを付ける、という二段構えになる。

このポートフォリオの SA は2つ。fetch-daily-prices は BigQuery に書くので bigquery.dataEditor（テーブルに書く）と bigquery.jobUser（ロードジョブを投げる）の2つ。scheduler-invoker は Job を起動するだけなので run.invoker を、しかも Job 単位で付ける。起動する側にデータを書く権限は要らない、これが最小権限の実例で、面接で「なぜ SA を分けたか」と聞かれた時の答えになる。SA のキー（JSON）は作らない。アタッチすれば要らないし、漏れるのはだいたいキーだから。

2. BigQuery：置き場・ジョブ・課金の考え方

BigQuery はストレージとコンピュートが分かれている。データは列指向で保存され、クエリのたびに必要な列だけ読む。AWS でいえば Redshift より Athena に近く、課金は「読んだバイト数」で決まる（オンデマンド）。クエリは必要な列を丸ごと読む（行を1件ずつ引くためのインデックスは持たない）。読んだ量がそのまま仕事量なので、そこに課金する。無料枠は月 1 TiB のクエリと 10 GiB のストレージ。

データセットはテーブルの入れ物で、Glue のデータベースに相当する。1つ違うのはリージョンを持つこと。asia-northeast1 で作ったデータセットは後から動かせないし、別リージョンのテーブルと JOIN できない。だから全部を東京に揃えている。テーブルは プロジェクト.データセット.テーブル の3階層で指定し、他プロジェクトの公開データ（bigquery-public-data.…）も同じ書き方で読める。

ジョブは BigQuery への1回の依頼の単位。ロード（ファイルや DataFrame を入れる）、クエリ、エクスポート、コピーの4種類があり、全部がジョブとして「ジョブ履歴」に6か月残る。Python の load_table_from_dataframe はロードジョブを、client.query() はクエリジョブを作る。ここで大事なのは、課金バイトが付くのはクエリジョブだけということ。ロードは無料。だから maximum_bytes_billed という上限は、日次の取得ジョブ（ロード）には効かず、staging / mart を作るクエリにだけ効く。

処理バイトと課金バイトは普通一致するが、ズレる場面が3つある。キャッシュに当たった時（課金 0）、パーティションで読まなかった時（見積もりより減る）、最低課金単位（10 MB 未満は切り上げ）。maximum_bytes_billed は実行前の見積もりと比較され、超えていれば走らずに拒否される。見積もりは --dry_run で見られる。この「実行前に止まる」性質があるから、課金の安全装置として唯一確実な層になる。

パーティションは日付などでテーブルを内部的に分割する仕組みで、WHERE date >= … のようにパーティション列で絞ると該当分だけ読む（プルーニング）。クラスタは各パーティション内を指定列（ticker）で並べ替えておく仕組みで、絞り込みと集計がさらに軽くなる。どちらもテーブル作成時にしか付けられない。既存テーブルに後から付けるには作り直すしかなく、Terraform ではそれが replace として現れる（第4章）。

ロードの流儀。WRITE_TRUNCATE は「全部消して入れ直す」、WRITE_APPEND は「後ろに足す」。日足は「直近1年をまるごと毎回取り直す」設計なので TRUNCATE が正しい。同じジョブを何回流しても結果が同じ、これが冪等性で、失敗した時に安心して再実行できる理由になる。ただし TRUNCATE が正解なのは「全量を取り直せる」時だけで、分足のように 60 日しか遡れないデータでは全体を消せない。その場合は テーブル$20260901 のようにパーティション1つを指定して、その日だけを置き換える。ロード方式は取得設計とセットで決まる。

スキーマの所有者。ロードジョブにスキーマを渡さないと、BigQuery は DataFrame の型から毎回スキーマを推定し、テーブル定義を上書きする（autodetect）。pandas 由来の推定は NULLABLE や旧式の FLOAT になり、Terraform が宣言した REQUIRED / FLOAT64 とズレる。8/25 の事故はこれで、terraform plan が「宣言と違うから作り直す」と replace を提案した。対策は LoadJobConfig(schema=[…]) で明示すること。テーブルの構造は Terraform、中身は Python、定義の持ち主を1つに決める。

3. 動かす側：Cloud Run Jobs・Artifact Registry・Scheduler・Secret

Cloud Run には Service と Job がある。Service は常駐して HTTP を受ける（ECS Service や Lambda + API Gateway）。Job は起動して処理して終了する（ECS Fargate の RunTask）。バッチはこちら。Job は「定義」（どのイメージを、どの SA で、どの環境変数で）と「実行（execution）」が分かれていて、gcloud run jobs execute は定義から実行を1つ作る。実行履歴とログはコンソールの Job ページに残る。イメージを更新しても Job 定義は古いタグを指したままなので、タグを v2 にして定義側を更新する必要がある。

Artifact Registry は ECR。docker build → docker push で置き、Job がそこから pull する。Dockerfile で requirements.txt を先に COPY するのはレイヤーキャッシュを効かせるためで、コードだけ変えた時に pip install をやり直さない。

Cloud Scheduler は EventBridge Scheduler。cron の時刻に HTTP リクエストを1本投げるだけの部品で、それ以上のことはしない。Job を起動するには https://run.googleapis.com/v2/projects/…/jobs/JOB:run に POST する。ここで認証が要る。宛先が Google の API なので OAuth トークンを使う（SA のメールを指定すると Scheduler がトークンを取って付けてくれる）。自分で立てた Cloud Run Service を叩く時は OIDC トークン。「Google API を呼ぶなら OAuth、自前エンドポイントなら OIDC」と覚えれば足りる。そして Scheduler の SA には対象 Job の run.invoker が要る。403 が出たらほぼこれ。

複数の Job の順序（raw → staging → mart）は、今回は時刻をずらして制御する。実務なら Workflows か Airflow（Cloud Composer）で依存関係を書くのが定石だが、Composer は個人で回すには課金が重い。「なぜ Composer を使わなかったか」は設計判断メモの1本になる。

Secret Manager は API キーの置き場（AWS の Secrets Manager / SSM SecureString）。Job 定義で「この環境変数はこのシークレットの最新版」と指定すると、起動時に展開される。Job の SA に secretmanager.secretAccessor が要る。キーをイメージや tfstate や Git に書かないための部品。

4. Terraform：宣言・state・plan・replace

CloudFormation と同じ宣言型だが、決定的に違うのが state。CloudFormation はスタックの状態を AWS が持つ。Terraform は terraform.tfstate というファイルを自分で持ち、そこに「この宣言はこの実リソースに対応する」という対応表を書く。plan は宣言・state・実体の3つを突き合わせて差分を出す。だから state が壊れたり消えたりすると、Terraform はリソースを見失う。チームでは GCS バケットに置いてロックを効かせるのが定石で、個人・単一端末の今回はローカルに置く（README に明記する）。

plan の読み方は3種類だけ覚える。+ 作成、~ その場で変更、-/+ 作り直し（replace）。replace はテーブルなら中身が消える。replace になるのは「作成後に変えられない属性」を変えた時で、BigQuery ならパーティション設定やデータセットのリージョン、スキーマの REQUIRED ↔ NULLABLE がそれ。CloudFormation の「置換が必要な更新」と同じ。

ドリフトは、Terraform の外から実体が変わって宣言とズレること。8/25 は Python がスキーマを書き換え、8/30 にも同型が起きた。Terraform は「宣言が正」なので、ズレを見つけると実体を宣言に戻そうとし、それが replace になる。日次で自動実行されるパイプラインでドリフトが常態化すると、うっかり apply した日にデータが消える。対策は第2章の「定義の持ち主を1つに」。

apply 前の約束事は1つ。plan に -/+ か destroy があったら止まる。 許すのは「バックフィルで戻せる」と自分で言える時だけ。

5. データ基盤の考え方：層・冪等・as-of・品質・監視

raw / staging / mart は dbt でいう staging / intermediate / marts と同じ発想。raw は取得元のまま置く層で、「パイプラインでこれ以上遡れない入力の境界」。ここを加工すると、後で計算を直したくなった時に元に戻れない。yfinance で auto_adjust=False にしたのはそのためで、調整済みの値を raw に入れると「調整後終値を自分で再計算する」見せ場が成立しなくなる。staging は型を揃え、重複を消し、変な値にフラグを付ける（落とさない）。mart は見せる形。ファクト（日々の価格、四半期のファンダ、マクロ指標）とディメンション（銘柄マスタ）に分けるスタースキーマで、BI ツールが読みやすい。

冪等性は「同じ処理を2回やっても結果が同じ」。バッチが失敗した時に「もう一回流していいか」を判断する根拠になる。全量置き換え（TRUNCATE）、パーティション置換、CREATE OR REPLACE TABLE、どれも冪等。APPEND は冪等でない。DATUM の Ops 職の業務にある「再実行判断」は、この性質を知っているかを聞いている。

as-of ジョインは「その日時点で知り得た最新の値を付ける」結合。四半期決算は提出日（filed_date）以降にしか分からないので、filed_date <= date で絞ってから最新1件を取る。期末日で結ぶと未来の情報を過去に付けてしまう（ルックアヘッド）。金融データの基本作法で、見せ場の2つ目。

データ品質テストは、合成データだと自作自演になる。実データには本物の欠損がある。外国籍の銘柄（TSM、ASML など）は IFRS で報告するので us-gaap の項目が無い。FRED は欠損を "." で返す。Yahoo の調整後終値は自分の再計算と 100% は一致しない。これらを「検知して、落とさず、記録する」のがテストで、閾値（一致率 95% など）は自分で決めて理由を書く。

監視は4種類に分ける。失敗（ジョブが落ちた）、鮮度（今日のデータが来ていない）、品質（行数が急減した、一致率が下がった）、コスト（課金バイトが跳ねた）。鮮度と品質は SQL の ASSERT でジョブ自体を失敗させると、失敗の通知経路に乗る。W7 では、わざと壊して、検知して、再実行してよいか判断して、直す、を1回記録する。

6. コストの3層（有料化後に効く）

  1. 予算アラート：金額を超えたらメール。通知だけで課金は止まらない
  2. maximum_bytes_billed：クエリ1本ごとに実行前で止める。唯一確実
  3. カスタム割り当て（1日あたり）：プロジェクト全体の上限。無料トライアル中は変更不可、11/1 の有料化後に設定。公式に「おおよその値」と明記されている

無料トライアル中は $300 を使い切ると止まるので、実質のハードリミットが既にある。有料化するとそれが外れる、だから 11/1 に 2 と 3 を揃える。
